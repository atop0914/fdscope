# 设计说明：为什么是「指纹」

## 1. 问题的形状

`too many open files` 的排障难点不在「发现」，而在「归因」。

发现很容易：`ls /proc/<pid>/fd | wc -l` 一直在涨，或者 Prometheus 里
`process_open_fds` 单调上升。但运维拿到这个数字之后能做的事只有两件 ——
重启，或者回家。

**能不能不重启就定位到泄漏源？** 这是 fdscope 唯一的立足点。

## 2. 为什么原始数据不能直接用

`/proc/<pid>/fd/N` 是一个符号链接，读出来是内核认为这个 fd 指向什么。
看起来非常适合分组 —— 同名的一律归成一类。但直接用会得到**完全错误的结论**。

### 2.1 socket 的 inode 每次重连都变

```
socket:[1234567]
socket:[1234891]   ← 同一个连接池，重连一次就是新 inode
socket:[1240012]
```

一个泄漏的 HTTP 连接池在 `lsof` 里看起来是 **几千个不同的资源**，
而实际上只有 **一个**。如果按原始 target 分组，你会得到几千行 count=1 的表格，
每一行都不像是问题 —— 泄漏因此被淹没在噪音里。

### 2.2 日志轮转把同一个文件切成很多个名字

```
/var/log/app.log
/var/log/app.log.1
/var/log/app.log.2026-10-22
```

一个持有旧轮转文件没关的 bug，每天产生一个新 target。
按原始 target 分组，它是「每天多一行 count=1」；按指纹分组，
它是「`file:/var/log/app.log` 的 count 每天 +1」—— 这才是可观测的形状。

### 2.3 已删除文件与存活文件长得很像

```
/tmp/scratch
/tmp/scratch (deleted)
```

这两个**必须分开**。存活文件泄漏只是占一个 fd；已删除文件泄漏在占 fd 的同时
**还在占磁盘**，而且 `du` 完全看不到（`lsof | grep deleted` 才能看到）。
把两者合并会让「磁盘被谁吃了」这个更严重的问题隐身。

## 3. 指纹的三条规则

### 规则一：只保留能证明的部分

`socket:[12345]` 里唯一有信息量的部分是「这是个 socket」。
inode 数字只是这次连接的实例 id，对「哪个资源在泄漏」毫无贡献。
所以指纹是 `socket`，不带 inode。

同理 `pipe`。而 `anon_inode:[eventpoll]` 的 `eventpoll` 是有意义的
（它告诉你这是 epoll 实例而不是 inotify），所以保留 payload、丢掉实例数字。

### 规则二：合并「几乎总是同一个东西」的，分开「几乎总是不同东西」的

| 合并 | 理由 |
|------|------|
| 日志轮转（`.1` / `.2026-10-22` / `-20261022`） | 几乎总是同一个写入者 |
| socket / pipe 的 inode | inode 是实例 id，不是资源 id |

| 分开 | 理由 |
|------|------|
| `file:/a.log` 与 `file:/sub/a.log` | 同名不同目录是两个真实的泄漏 |
| `file:/tmp/x` 与 `deleted:/tmp/x` | 后者还占着磁盘，是更严重的问题 |
| `socket` 与 `pipe` | 不同种类的资源，修复方向完全不同 |

**这一条是设计里最容易搞错的地方**。合并过头会把两个泄漏揉成一个
（大的那个被平均掉）；分得太细则退化成噪音。fdscope 的默认规则偏向「少合并」，
因为漏报一个泄漏比多显示一行要安全。

### 规则三：必须幂等

把指纹再喂给归一化函数，结果必须一模一样。

第一版没做这件事，后果是静默的：报告层在二次分组时会得到
`file:file:/a` —— 一个永远不会与任何其他行匹配的字符串，于是所有行都不再合并，
表格退化成「每行 count=1」。

这个 bug 是被 `TestFingerprintIsIdempotent` 抓到的，不是靠读代码发现的。
**幂等性必须写成断言**，因为它失效时不会报错，只会让聚合悄悄失效。

## 4. `/proc` 能证明什么，不能证明什么

这是本项目最重要的一张表。**工具的价值取决于它不撒谎。**

| 想知道 | `/proc` 给不给 | fdscope 的处置 |
|--------|---------------|---------------|
| 有几个 fd | ✅ `/proc/<pid>/fd` 目录项 | 直接报 |
| 每个 fd 指向什么 | ✅ `readlink` | 直接报 |
| 文件是否已被删除 | ✅ target 尾部 ` (deleted)` | 单独标记 |
| 读写偏移与打开模式 | ✅ `fdinfo` 的 `pos` / `flags` | 解析但只作辅助 |
| 进程的 fd 上限 | ✅ `/proc/<pid>/limits` 的 soft limit | 报余量 |
| **是谁打开的** | ❌ | **不编造**。见下节 |
| 打开时间 | ❌（`fdinfo` 没有时间戳） | 只能用采样推断「首次出现」 |
| socket 的对端地址 | ❌（只有 inode） | 不做 |
| 打开时的调用栈 | ❌ | 仅作为库使用时「有条件地」获取，见下节 |

`/proc` 的读数是**瞬时且非原子**的：读目录与读链接之间 fd 可能已经被关掉。
fdscope 把读不到的项计入 `Unreadable`，并把总数标明为下界 ——
因为「读失败」和「真的少了」在数字上完全一样，不区分就会得出「fd 下降了」的假结论。

## 5. 归因：宁可少说，不许胡说

「谁打开的这个 fd」在 `/proc` 里没有答案。要做到它需要三条不同强度的路径，
fdscope 把它们分成三层，并且**每层都必须标注自己的强度**：

### L1 类型 / 路径归因（可证明）

指纹本身已经是归因。`file:/var/log/app.log` 直接告诉你去看日志模块。
这一层没有猜测成分。

### L2 时序归因（相关性，不是因果）

泄漏的 fd 在 T 时刻开始上涨。如果同一个进程在 T 时刻有某个 HTTP 路由被频繁调用，
那是**相关**。相关不等于因果 —— 可能是那个路由，也可能是同时在跑的定时任务。

**规则**：L2 的输出必须带「相关性」标签和样本数。任何看起来像因果的措辞
（「这个路由导致了泄漏」）都是 bug。

### L3 调用点归因（仅限作为库使用）

只有在进程内使用 fdscope（`pkg/fdscope`）时，才可能在 fd 数量变化的瞬间
抓 `runtime.Stack`，把「这次变化」与「这些 goroutine 栈」配对。
这仍然不是精确的「谁 open 的」—— 栈是采样时刻的快照，不是打开时的快照。

**规则**：L3 只在确实能采样到时输出，采样不到就明说采样不到。

### 明确不做的事

- 不 ptrace（会改变被测进程行为，且在容器里常常没权限）
- 不解析二进制符号表猜调用者
- 不因为「看起来像」就下结论

## 6. 误报比漏报更致命

一个会在正常上涨时报泄漏的工具，第二天就没人看了。

因此 fdscope 的判定把「正常但会涨」的行为当作一等公民：

| 场景 | 为什么它正常 | fdscope 必须怎么做 |
|------|-------------|-------------------|
| 连接池预热 | 启动后 fd 从 10 涨到 200 再不变 | 建立基线**之后**才判定；预热期不算泄漏 |
| 批量打开再批量关闭 | 短暂峰值 | 看**回落**：涨上去又能下来 = 不是泄漏 |
| 周期性波动 | 定时任务开文件 | 看**单调性**：真泄漏不会回落 |
| 目录遍历 | 瞬时大量打开 | 看**持久度**：泄漏的 fd 会一直在 |

**判据设计**：单调增长 + 不回落 + 超过基线一定比例。
三个条件都满足才报。这一个组合是「防误报」的主要机制，
验收里专门有一组「必须不报」的语料守着它。

## 7. 为什么不做平台兜底

在 darwin/windows 上返回空快照看起来「兼容」，实际上是有害的：

```go
snap, _ := probe.Snapshot(pid)   // 非 Linux 返回 0 个 fd
if snap.Len() > threshold { ...  // 永远不成立 → 永远判「没泄漏」
```

一个看不见的工具必须**说自己看不见**，而不是报告「一切正常」。
所以非 Linux 上 `IsSupported()` 返回 false、`Snapshot` 返回 `ErrNotLinux`，
CI 里有 `build-check` 保证所有平台**能编译**（可以诚实地说"不支持"），
但不能**假装支持**。

## 8. 差异比较：为什么按指纹而不是按 fd 号

`diff` 的输入是两个时刻的快照，输出是「什么变了」。这里有一个看起来无害、
实际会让工具撒谎的选择：按什么比对。

### 8.1 fd 号会被立刻回收

```
t1: fd 7 -> /var/log/old.log
     (关闭 7，再打开新文件 → 内核把 7 还给你)
t2: fd 7 -> /var/log/new.log
```

两份快照的 fd 集合完全相同、总数完全相同。**按 fd 号比对会报「无变化」**，
而这正是本项目存在的理由：一个资源被释放、另一个被获取。
按指纹比对才会出现两行（一个消失、一个新增），`net_change` 仍然是 0 ——
所以「总数没变」永远不能当作「什么都没发生」。

### 8.2 反过来的坑：socket 重连不是变化

同一个连接池重连 1000 次，`socket:[inode]` 每次都不同，但指纹都是 `socket`。
如果按原始 target 比对，一个泄漏会被报成 1000 次独立变化。
指纹归一化让这种情况**不产生噪音** —— 这也是「只读进程必须报无变化」这条
反向断言守的东西。

### 8.3 pid 会被回收：start time 是唯一的身份

`Before.PID == After.PID` 证明不了是同一个进程。pid 一旦被回收，
新的进程可以拿到同一个号，把两份快照相减会得到一份**看起来很专业、
但完全是虚构的**变化清单。所以 `Compare` 要求两次采样读到的
`/proc/<pid>/stat` 第 22 字段（启动时间）相等；读不到就报错，不假设相等。

### 8.4 不完整的快照不能相减

读不到的 fd 与「被关闭的 fd」在数字上完全一样。部分快照会产生**幽灵「消失了」**
条目，并可能掩盖真实的「新增」。所以 `Unreadable > 0` 直接拒绝相减。

### 8.5 已删文件：给出路径，但绝不编造大小

`deleted:` 视图回答的是 `du` 结构上答不了的问题：这些文件没有目录项，
没有任何遍历能看到它们。fdscope 报**路径 + 持有它的 fd 数 + 其中几个是写模式**。

**不给字节数**：路径已经不存在，`stat` 无从下手；剩下的路子（`map_files`、
对目标进程的 fd 做 fstat）都要越界操作，本项目明确不做。给一个猜的数字，
恰恰摧毁了这个视图唯一的价值。

顺带一个真实发现：`WRITABLE` 一列来自 `fdinfo` 的 `flags` 位（`O_WRONLY` /
`O_RDWR`）。只读持有的已删文件钉住的是 inode；**写模式持有**的才真正占着
磁盘块。这一列此前在 `model.Descriptor.Flags` 里存在但没有任何消费者。

## 9. 时间序列：为什么「两点之差」不够

`diff` 只能看见两个端点。一个进程在 t1 有 100 个 fd、t2 有 140 个，这个事实同时
符合三种完全不同的真相：真泄漏、连接池预热、批处理跑到一半。**区别只在中间的形状里**。

`watch` 把过程录下来（`internal/timeline`），由 `internal/analyze` 判定形状。

### 9.1 有界内存不是优化，是正确性要求

`watch` 的用途是盯着一个服务跑几天。保留全部样本会让**审计工具自己变成泄漏源** ——
运维第一眼看到的会是 fdscope 进程在涨，而那会连同报告里的每个数字一起失去信任。
所以容器是环形缓冲，被挤掉的样本数单独计数（`dropped`），报告里必须写
「最近 60 个，共 5000 个」，而不是假装从头看起。

断言落在**容器实际报告的长度**上，不是回显配置值：一个「保留最老样本」的实现
同样能通过容量检查，但它报的是一段早已结束的历史。

### 9.2 回落的三个条件，每条都排除一种误报

```
回落 = 先上升到峰值 → 从峰值下降 ≥ 阈值
```

- **峰值前必须先有上升**：单调下降 100→40 是回收，不是回落。少了这条，每次
  进程退出都会被记成「批处理」。
- **从峰值算，不从首样本算**：10→100→40 确实释放了 60，即使终值高于起点。
- **下降要达到阈值**：fd 数在健康进程里也会抖 1~2，把它报成回落会让人
  彻底忽略这一列。

**报的是峰值之后的最低点，不是终值**：100→40→80 证明了释放 60，
报「-20」会低估工具唯一能证明的东西。

### 9.3 趋势比端点，不拟合斜率

三个样本 100/101/100 的最小二乘斜率不是 0，会读成「有趋势」。端点差 + 容差
回答的是读者真正在问的问题（「比我开始看的时候高了吗」），并且在答案是无所谓时保持沉默。

### 9.4 ⚠️ 僵尸进程的 `/proc/<pid>/fd` 是**空目录**，不是不存在

这是本轮抓到的真实缺陷，也是本项目最危险的失效模式。

进程退出但还没被回收时，`/proc/<pid>` 依然存在，`readdir(/fd)` **不报错，而是返回空**。
而「空 fd 集合」对活进程是完全合法的状态，所以任何只看「有没有报错」的实现都会
把它读成一次成功的采样 —— 于是**所有 fd 在进程死亡那一刻被报告为「已释放」**，
泄漏审计的结论正好反转，而且输出里没有任何迹象。

修法：`Snapshot` 现在会读 `/proc/<pid>/stat` 第 3 字段，遇到 `Z` 直接返回
`ErrProcessExited`。顺带纠正一个观念：`Exists()` 对僵尸返回 true，
它从来就不是存活检查。

### 9.5 采样看不见两次采样之间的突变

这是采样式工具的固有限制，不是 bug，但必须写清楚：一个在 t 到 t+Δ 之间
打开又关闭的 fd，采样器**永远不会知道**。所以「没看到变化」只能读成
「在我看的那些时刻没有变化」。

推论对测试同样成立：**把变化放进两次采样之间**才是被验证的场景。
本轮的 6 个 watch 场景里，有 3 个第一次是这么写错的（变化全压缩在一个间隙里），
症状却是「实现不判回落」——差点去改实现。

### 9.6 中途失败必须保留已采样本

进程在第 40 个采样前死掉，前面 39 个样本是证据，而且**突然中断的序列往往是
最有意思的部分**。所以 `Watch` 把失败放进返回值里（`WatchResult.Err`），
CLI 先渲染报告再返回非零退出码与错误。丢弃证据以换取一个干净的错误是本末倒置。

## 10. 泄漏判定：从「形状」到「结论」

`watch` 回答「在涨吗」，`--judge` 回答「是泄漏吗」。两者刻意分开：一个上涨的序列
同时也是连接池预热、批处理跑到一半、目录遍历。五条判据全部成立才判泄漏，
每条都排除一种特定的误报形状：

| 判据 | 排除什么 | 证据字段 |
|------|---------|---------|
| 单调性 | 涨了又下来 = 干完活了 | `monotonic` / `fallback_after_peak` |
| 增长下限 | 1→5（400%）不是泄漏 | `growth` / `growth_required` |
| 速率下限 | 「很久涨了很多」是 ramp-up | `rate_per_second` / `rate_required` |
| 基线（预热期排除） | 每个刚启动的服务都在填池子 | `baseline_value` / `warmup_samples` |
| 覆盖度 | 增长必须铺开、且窗口结束时还在爬 | `active_gaps` / `total_gaps` |

**每个判定都必须带得出触发它的数字**，否则结论就是意见。`--judge` 的表格
逐项打印测量值与阈值，读者可以用工具自己的数字反驳工具。

### 10.1 预热期的截止点要**测量**，不能**假定**

`warmup` 最初写成「切掉序列前 20%」。这隐含假设增长是均匀铺开的，
而真实泄漏不是：对一个活进程实测，30 → 99 的爬升里有 33 个（将近一半）
发生在窗口前 20% 之内。于是基线被取在 63，剩下的爬升看起来
「只在 23 个间隙里涨了 6 个，且到窗口末尾已经停了」—— 对一个
最 unambiguous 的泄漏给出了 no-leak。

改成 `stablePrefix`：预热期结束于计数**第一次离开起始水平**的位置，
用的是与形状层同一个 `DefaultFlatTolerance`，让两层对「移动」的定义一致。
从第一个样本就在爬的序列没有预热期可排除。

**填空式的池子仍被排除**，靠的是本来就在真正干活的那条判据：它的增长
集中在头部、窗口末尾是平台，`sustainedGrowth` 会拒绝它。
`TestStartupFillStillExcluded` 成对守着这一点，所以这个修法
不能被「干脆删掉预热排除」满足。

### 10.2 尾部平台必须看**一段**间隙，不能只看最后一个

连续性判据曾以「最后一个间隙必须增长」结尾。这对步进式泄漏是掷硬币：
进程每 200ms 开 3 个 fd、采样每 120ms 一次，序列就是 3,0,3,0 交替，
最后一个间隙是否为 0 由**相位**决定，与进程行为无关。
实测同一夹具两次运行，一次判 LEAK、一次判「窗口末尾已停止」。
**在两次相同运行之间会翻转的判定不是判定。**

改为统计**尾部连续不增长的间隙数**，允许占窗口间隙总数的四分之一。
步进式泄漏的零间隙是一个样本宽、后面必然跟着增长；而填完就停的池子
从最后一次步进之后全是平的，在任何值得判定的窗口里都远超四分之一。

### 10.3 判定必须可复现：`--series`

`--judge --json --series` 输出逐点总量。这不是调试开关，是**结论的可审计性**：
一个无法用它的输入复现的判定只是意见。上面 10.1 和 10.2 两个缺陷被发现，
靠的正是「输出的形状摘要与结论自相矛盾」（`total rising 30 -> 99` 旁边写着
`no leak`），而只有逐点序列能在一行内回答是哪一边错了。

## 11. 已知边界（v1 阶段）

- `watch` 采样，**看不见两次采样之间的突变**（见 9.5）：一个在间隙里打开又关闭的
  fd 永远不可见。「没看到变化」只能读成「在我看的那些时刻没有变化」
- `watch` 默认只做形状判定（趋势 / 回落）。加 `--judge` 才给泄漏结论：
  单调上升也可能是预热或慢批处理，判定必须是显式请求，而不是默认态度
- **泄漏判定看不见窗口之前的增长**：如果 fd 在采样开始前就已全部打开，
  序列是平的。这类「事后才发现」的泄漏只在两种条件下被判：序列自己首个样本
  更低（期间确有上涨），或恒定计数已占 limit 的 50% 以上。两者都只给
  **low** 置信度，并在 reason 里写明「增长早于采样窗口」——把弱证据说成强结论
  是本项目最容易堕落的方式
- 回落阈值是绝对值，全进程共用一套。一个持有 5 个 fd 的进程与持有 5 万个的进程
  需要不同尺度，目前只能靠 `--rebound` 手工调
- `diff` 只比较两个端点，不做自动泄漏判定（需要单调性 + 回落）
- `diff` 无法区分「采样窗口内短暂打开又关闭」与「一直没变」—— 端点之间的
  变化完全不可见，这是采样式工具的固有限制，不是 bug
- 没有归因（Day 7-9）
- 不处理 PID namespace / 容器边界的坐标转换：在容器内跑 fdscope 看容器内的 pid，
  在宿主机跑看到的是宿主机的 pid，两者不自动对应
